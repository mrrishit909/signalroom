# Metric definitions (each defined once, no restating elsewhere)

All figures below are computed from the synthetic seeded dataset in `data/raw/`
(generated by `data/generate_seed_data.py`, seed 20260101). They describe no real
retailer, real transactions, or real customers.

## Transaction status

Every order has exactly one status: `completed`, `returned`, or `cancelled`.
A `cancelled` order's items contribute **zero** revenue, COGS, discount, or margin
anywhere. A `returned` order's items contribute the **negative** of what a
`completed` order with identical items would have contributed, so a fully-returned
order always nets to exactly zero in every metric below.

## Revenue

- **Gross revenue** = `quantity * list_price` (the undiscounted reference price),
  for every item regardless of status. Numerator: `sum(gross_revenue)`.
- **Discount amount** = `quantity * max(list_price - unit_price, 0)`. Only non-zero
  during an active promo window (`data/generate_seed_data.py:PROMO_WINDOWS`).
- **Net revenue** = signed per-status contribution defined above
  (`+quantity*unit_price` completed, `-quantity*unit_price` returned, `0` cancelled).
  This is the number shown as "Revenue" anywhere on the site.

## Cost and margin

- **COGS** mirrors net revenue's sign: `+quantity*unit_cost` completed,
  `-quantity*unit_cost` returned, `0` cancelled.
- **Margin** = `net_revenue - cogs`. **Margin %** = `margin / net_revenue` where
  `net_revenue != 0`, else excluded from the denominator (never divide by zero,
  never silently show 0%).

## Average order value (AOV)

`sum(net_revenue) / count(distinct order_id)` over `completed` orders only in the
selected filter window. Returned and cancelled orders are excluded from the
denominator (they were never a "completed" sale) but a returned order's negative
net_revenue is still excluded from the numerator for the same reason, not netted in.

**AOV and completed-order counts are sliced by region/channel/month ONLY, never
by category.** An order can contain items from more than one category (a single
checkout with a jacket and a pair of boots), so "the number of completed orders
in category X" cannot be computed by pre-aggregating a per-category distinct
count and summing across categories -- that double-counts any order that spans
categories. The site's `orders_monthly` grain is built at region x channel x
month only, deliberately excluding category, so it stays additive under any
combination of region/channel/month filters. Applying a category filter changes
the revenue/margin/units figures shown but does NOT change the completed-order
count or AOV; the UI labels this explicitly rather than showing a silently wrong
number. (This was caught by the aggregator's own parity test against a
from-scratch SQL query -- see `site/src/lib/aggregate.parity.test.ts`.)

## Retention (cohort)

A customer's cohort month = the calendar month of their first `completed` order
(not their `signup_date`, which can precede any purchase). Retention in month N =
`count(distinct customers with >=1 completed order in cohort_month + N) / count(distinct customers in cohort_month)`.

## Reconciliation gate (spec criterion 02)

`tests/reconciliation_fact_sales_matches_raw.sql` recomputes net_revenue directly
from the raw seeds (bypassing every mart/staging model) and fails the build if a
single `fact_sales` row's `net_revenue` or row count disagrees with that
independent computation by more than $0.001, or if any row is missing on either
side (which would mean a join fan-out or drop). Every chart, tooltip, and export on
the site traces to a SQL query that filters `fact_sales`/`fact_inventory` by the
same dimension keys the UI exposes, so what you see always matches what `dbt test`
verified.
